# Causal Event Ledger v1

## Authority and Scope

This document follows `AGENTS.md` as the sole authority. It defines a conceptual,
append-only historical record for Earthly.

It does not implement a ledger, modify tickManager, alter intent generation,
change simulation outcomes, add persistence behavior, or modify existing
schemas.

## Core Contract

```text
Simulation Authority owns live causal truth during execution.
Causal Event Ledger owns immutable historical truth after execution.
```

Every committed simulation-relevant state change must be representable by one
or more causal events.

The Ledger records what already happened. It never decides what should happen.

## 1. Event Ontology

### 1.1 Biological Events

| Event Type | Meaning |
| --- | --- |
| `BirthEvent` | A new biological agent entered live simulation state |
| `DeathEvent` | An agent completed the lifecycle transition to death |
| `AgingEvent` | An agent's temporal age or life stage changed |
| `InjuryEvent` | A committed interaction reduced biological condition |
| `DiseaseEvent` | A committed disease-state transition occurred |

### 1.2 Interaction Events

| Event Type | Meaning |
| --- | --- |
| `CombatEvent` | A combat interaction was executed |
| `HuntEvent` | A hunt interaction was executed |
| `TradeEvent` | A resource exchange interaction was executed |
| `CooperationEvent` | Agents completed a cooperative interaction |
| `BondFormationEvent` | A committed relationship-state transition occurred |

### 1.3 Economic and Environmental Events

| Event Type | Meaning |
| --- | --- |
| `ResourceConsumptionEvent` | A committed action reduced a resource |
| `ResourceGenerationEvent` | A committed process increased a resource |
| `MigrationEvent` | An agent or population completed relocation |
| `StarvationEvent` | A committed biological starvation transition occurred |

### 1.4 System Events

| Event Type | Meaning |
| --- | --- |
| `TickStartEvent` | Marks the deterministic beginning of a tick |
| `TickEndEvent` | Marks the deterministic completion of a tick |
| `IntentGeneratedEvent` | Records that an intent output was produced |
| `ActionExecutedEvent` | Records that a validated action was executed |

### Event classification rule

An event records a completed or observed fact. It must not contain an executable
instruction.

```text
Valid event: ActionExecutedEvent records action X was committed.
Invalid event: ActionExecutedEvent tells tickManager to execute action X.
```

`IntentGeneratedEvent` is informational. It records that the Decision Layer
produced an intent artifact. It does not make the intent executable and must not
be generated by the intentPipeline itself.

## 2. Event Schema Definition

Conceptual event shape:

```ts
type CausalEvent = {
  eventId: string;
  tickId: number;
  sequence: number;
  timestamp: number;
  eventType: CausalEventType;
  actorId?: string;
  targetId?: string;
  stateBefore?: SnapshotReference;
  stateAfter?: SnapshotReference;
  causalReason?: TraceReference;
};
```

### Required fields

| Field | Requirement |
| --- | --- |
| `eventId` | Globally unique, deterministic identifier |
| `tickId` | Tick in which the recorded fact occurred |
| `sequence` | Deterministic event ordering within the tick |
| `timestamp` | Simulation timestamp, never wall-clock authority |
| `eventType` | Canonical ontology type |

### Optional fields

| Field | Meaning |
| --- | --- |
| `actorId` | Entity whose action or transition produced the event |
| `targetId` | Entity or state domain affected by the event |
| `stateBefore` | Immutable reference to pre-commit state |
| `stateAfter` | Immutable reference to post-commit state |
| `causalReason` | Immutable reference to a trace explaining why |

### Snapshot-reference rule

`stateBefore` and `stateAfter` must be immutable references or content-addressed
snapshot identifiers. They must never contain live mutable simulation objects.

### Causal-reason rule

`causalReason` may reference Decision, Resolution, Execution, or lifecycle
traces. A trace explains causality; it does not become causal input.

## 3. Immutability Rules

### Append-only

Events may only be appended in deterministic order.

### No mutation

Once created, an event and all nested event data are immutable.

### No deletion

Events cannot be removed from canonical history.

### No rewriting

Corrections or reinterpretations must create new events or downstream
interpretations. They must never alter the original event.

### No mutable references

Events cannot retain references to live world, agent, intent, or UI objects.

### Historical identity

`eventId` identifies one immutable fact. Reusing an event ID for different
content is forbidden.

## 4. Source-of-Truth Rule

### Runtime truth

During a tick:

```text
tickManager / Execution Layer = authoritative live state
```

The Ledger must not be consulted to determine the current tick's behavior,
validation, or outcome.

### Historical truth

After a state transition has been committed:

```text
Causal Event Ledger = authoritative record that the transition occurred
```

Historical authority does not grant mutation authority.

### State and event relationship

```text
Committed state change -> causal event
```

Not:

```text
causal event -> live state mutation
```

The Ledger is not an event-sourcing execution engine in v1. It does not rebuild,
restore, rewind, or branch live simulation state.

## 5. System Interaction Boundaries

### tickManager / Execution Layer

May conceptually:

- Emit immutable event facts after committing state transitions
- Provide deterministic tick and sequence context
- Provide snapshot and trace references

Must not:

- Store the Ledger internally as live simulation state
- Read Ledger history for current decisions
- Rewrite or delete emitted events
- Delegate mutation authority to the Ledger

### Event recording boundary

A future recorder may accept completed event facts and append them to the
Ledger. The recorder owns append mechanics only. It does not own simulation
state or event meaning.

### intentPipeline / Decision Layer

Must not:

- Generate Ledger events
- Append to or mutate the Ledger
- Read Ledger history for intent scoring
- Treat historical events as direct state

The execution orchestration boundary may record an `IntentGeneratedEvent` after
the intent output exists.

### Trace Model

May:

- Explain why an event occurred
- Supply immutable causal-reason references

Must not:

- Replace the Ledger as canonical event history
- Influence event execution or simulation state

### Replay Model

May:

- Store immutable state frames associated with event ranges
- Visualize historical state

Must not:

- Rewrite Ledger events
- Restore or mutate live state in v1

### Derived and Analysis Layers

Culture, Settlement, Behavioral Signature, Civilization Memory, Civilization
Myth, Semantic Audit, and Causal Isolation may consume immutable Ledger views.

They must not:

- Append simulation events
- Rewrite canonical history
- Influence intent, resolution, execution, or live state

### Presentation and Persistence Layers

Presentation may display Ledger events only.

Persistence may serialize Ledger data only after a separate persistence contract
exists. Persistence is outside Causal Event Ledger v1 scope.

## 6. Determinism Guarantees

Given identical:

- initial state
- seed
- command/input stream
- simulation rules

the Ledger must produce identical:

- event count
- event types
- event IDs
- tick IDs
- sequence ordering
- actor and target references
- state snapshot references
- causal-reason references

### Deterministic event ID

A conceptual deterministic event identity may derive from:

```text
simulation identity + tickId + sequence + eventType + actorId + targetId
```

Random UUIDs and wall-clock timestamps must not define canonical event identity.

### Ordering rule

Events are ordered by:

```text
tickId ascending
then sequence ascending
```

Sequence assignment must follow declared execution order, never asynchronous
arrival order.

### Timestamp rule

Canonical `timestamp` represents deterministic simulation time. Wall-clock time
may exist as non-authoritative operational metadata outside the canonical event.

### Observer independence

Ledger output must remain identical regardless of:

- UI enabled or disabled
- Inspector active or inactive
- Analysis enabled or disabled
- Culture/Myth/Memory derivations executed or omitted
- Replay visualization enabled or disabled

## 7. Relationship Map to Existing Systems

```text
Decision outputs
    |
    v
tickManager / Execution Authority
    |
    +-> commits live state
    |
    +-> emits completed event facts
            |
            v
      Causal Event Ledger
            |
            +-> Trace references explain why
            +-> Replay frames show state at time
            +-> Behavioral Patterns
            +-> Settlement / Culture
            +-> Civilization Memory
            +-> Civilization Myth
            +-> Analysis / Inspector

Forbidden:
Ledger -X-> Decision
Ledger -X-> Execution
Derived interpretations -X-> Ledger rewrite
```

### Ledger versus Trace versus Replay

| System | Canonical Question | Authority |
| --- | --- | --- |
| Causal Event Ledger | What happened? | Immutable historical fact |
| Trace Model | Why did it happen? | Immutable causal explanation |
| Replay Model | What did state look like then? | Immutable historical snapshot |

These systems may reference each other but must not replace or mutate each
other.

### Life System relationship

Life state transitions may produce Birth, Aging, and Death events after those
transitions are committed. The Ledger does not control aging or death.

### Intent System relationship

The Ledger may record produced intent facts for history and debugging. It does
not feed historical intents back into scoring.

### Execution System relationship

Execution is the source of committed causal changes. The Ledger records those
changes after commitment.

### Culture, Myth, and Civilization Memory relationship

These downstream layers may derive patterns and interpretations from Ledger
history. Their outputs remain descriptive and cannot rewrite historical facts.

## 8. Future Extensibility Notes

### Event schema evolution

- New event types may be added without changing existing event meanings.
- Existing canonical event types must not be repurposed.
- Schema-version metadata may be added by a future contract.

### Event references

Future events may reference:

- parent causal events
- correlation groups
- interaction chains
- deterministic snapshot hashes
- trace hashes

References must remain acyclic with respect to event creation order unless a
future explicit graph contract permits otherwise.

### Aggregation

Long-horizon summaries, indexes, and compressed histories may be derived from
the Ledger. Aggregates are read models, not replacements for canonical events.

### Retention and persistence

Physical storage, compaction, archival retention, and export formats require a
separate persistence design. Logical history remains append-only even if
physical storage later uses segments or archives.

### Event sourcing

Rebuilding live state from the Ledger, branching timelines, or using events as
commands is explicitly outside v1. Those capabilities would require a separate
authority and determinism review.

## Contract Summary

```text
Execution commits reality.
Ledger records committed reality.
Trace explains committed reality.
Replay displays committed reality.
Derived systems interpret committed reality.
Nothing downstream changes reality.
```

Causal Event Ledger v1 establishes immutable causal history for all Earthly simulation events without affecting runtime behavior.
